# 返修机故障占比估算（FastAPI + NumPy）

备件前估算一批返修机中**电源 / 驱动 / 控制**三类故障各有多少台。
上传含「机器编号 + 分类器初判」的 CSV（≤500 台），维修班组随机拆检、
按台登记/更正/撤回实检类别，系统按实检样本拟合未检件的故障占比，
折算台数后加上各类实检数给出全批估计。

## 一、估算口径

1. 对已拆检机器，按**实检类别**分组，统计每组中各初判类别的经验概率，
   组成 3×3 混淆概率矩阵 `P`（行=实检，列=初判，每行和为 1）。
2. 未检件的初判经验分布为 `q`（各类未检件初判计数 / 未检台数，和为 1）。
3. 在单纯形约束 `π ≥ 0`、`Σπ = 1` 下，用 NumPy 求使平方误差
   `SSE = ‖Pᵀπ − q‖²` 最小的故障占比 `π`。求解器枚举内部点（等式 KKT）、
   三条边（一维解析解）和三个顶点，取 SSE 最小的可行解，矩阵亏秩时
   仍保证有候选返回（见 `app/estimation.py:_solve_simplex`）。
4. 各类估计台数 = 实检台数 + `π_k × 未检台数`（三类折算之和守恒为未检总数）。

### 门控规则

- **仍有未检件**时，若任一故障类别没有实检样本，或混淆矩阵不满秩
  （`numpy.linalg.matrix_rank` < 3），**撤下估数**并在页面提示补检原因。
- **全部拆完**时不做拟合，直接返回各类实检实数。
- 撤回一台后该台立即重新计入未检，门控与估数随之重算。

### 并发与一致性

- 拆检记录保存在单进程内存中，所有读写经同一把 `asyncio.Lock` 串行化。
  两个浏览器窗口同时登记/更正/撤回（含同一台机器）时，两笔修改都不丢失，
  接口返回的机器明细、实检数与估数始终来自持锁期间的同一份快照。
- 每次写入（登记/更正/撤回/换批）都会把记录**版本号** +1；批次快照与
  试算任务都带版本号，用于判断试算是否仍对应发起时那版记录。
- 因此部署固定 `uvicorn --workers 1`（见 `docker-compose.yml`）；
  多进程/多副本需换成数据库等共享存储。

## 二、抽检回放试算（全批拆完后）

用途：本批全部拆完后，用全检实检记录回放“只抽检 k 台”的估算效果，
为下一批安排抽检人手。

1. 页面「4. 抽检回放试算」填写**允许误差（台）**、**随机种子**和
   **1～6 档拆检台数**（每档 ≥ 1 台且少于全批，不得重复）。
2. 按种子生成 100 条**不放回**的随机拆检顺序；每条顺序对每个档位取开头
   的 k 台作为已检（沿用其真实实检类别），其余机器只保留初判，
   再调用现有 `estimate` 估算。同一条顺序下各档共享前缀，档位越大
   已检集合越大。
3. **单轮达标**：估数可用，且电源/驱动/控制三类**估计台数**与全检实数
   （`actual_total`）的绝对差都不超过允许误差。估数被门控撤下的轮次
   计入 `unavailable_count`，不算达标。
4. 页面显示各档 100 轮中的达标次数/未达标次数/达标率；**推荐量**为达标
   次数 ≥ 90 的**最小**档位，没有这样的档位时显示「未找到推荐量」。

### 失效规则（试算期间记录变化）

- 试算发起时对全检记录做快照并记下版本号，计算在独立线程（
  `asyncio.to_thread`）中执行，不占用事件循环：试算期间其他窗口仍可
  正常**更正、撤回或换批**。
- 任何写入都会推进版本号并立即作废基准版本不一致的任务；**改过又改回
  也算失效**（版本按写入次数单调递增，不比较内容）。
- 计算完成后还要在持锁状态下校验版本才落盘，迟到结果不会把已撤下的
  建议恢复；任务失效后 `result` 清空，只保留失效原因。
- 页面拿到新的批次版本时立即撤下旧建议；轮询返回的 `done` 若基准版本
  与页面当前版本不一致，同样不渲染。

## 三、目录结构

```
app/
  estimation.py     # 混淆矩阵、门控、单纯形约束最小二乘（纯 NumPy）
  csv_utils.py      # CSV 解析与校验（≤500 台、表头/类别别名、重复编号）
  storage.py        # 内存批次存储 + 异步锁 + 记录版本号
  simulation.py     # 回放试算：随机顺序、达标统计、推荐档位、任务失效
  main.py           # FastAPI 路由（含 /api/simulations）
  static/index.html # 单页前端（原生 JS，3 秒轮询同步多窗口改动）
scripts/
  generate_sample.py   # 生成演示 CSV（真实占比 45/35/20 + 混淆噪声）
  smoke_check.py       # 对运行中服务的端到端冒烟（含并发线程模拟两窗口）
  smoke_simulation.py  # 试算冒烟：有效试算 + 中途失效 + 换批失效
tests/              # pytest：求解器、门控、API、并发、试算与失效
data/sample_machines.csv  # 120 台示例数据
Dockerfile  docker-compose.yml  requirements.txt
```

## 四、启动方式

### Docker Compose（推荐演示）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

### 本地直接运行

```bash
pip install -r requirements.txt
python scripts/generate_sample.py 120 data/sample_machines.csv   # 可选
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

页面操作：上传 `data/sample_machines.csv` → 在机器行点击
「电源/驱动/控制」登记或更正 → 「撤回」使该台重算未检；
上方卡片实时显示实检数、未检折算、全批估计、`P`/`q`/`π` 与 SSE，
以及补检提示。全部拆完后，「4. 抽检回放试算」可填写允许误差、随机种子
和 1～6 档拆检台数，点击「开始试算」查看各档达标次数与推荐量。

### CSV 格式

表头支持 `机器编号,初判` 或 `id,initial`（UTF-8，含 BOM 亦可）；
类别支持中英文：`电源/power`、`驱动/drive`、`控制/control`。
编号不可重复，空行容忍，超过 500 台或类别非法返回 400 及中文原因。

## 六、已验证结果

- `pytest`：**27 项全部通过**（原 19 项 + 新增 8 项试算测试）。求解器与
  细网格暴力参考解在 12 组随机矩阵上交叉验证（SSE 不劣于参考解），覆盖
  精确还原、边界（零分量）解、缺类/不满秩门控、全检实数等场景；API 测试
  覆盖上传校验、登记、更正、撤回、400/404 错误路径及 `asyncio.gather`
  并发；试算测试覆盖档位校验、同种子可复现、达标次数合计=100、
  推荐最小达标档 / 无达标档返回 `None`、未全检/空快照拒绝、
  更正后又改回仍失效、迟到结果不恢复、换批失效。
- 真实 uvicorn 服务端到端冒烟 **全部 PASS**：上传 120 台 → 满秩样本下
  估数恢复且台数守恒（估数合计=120）→ 更正后实检数同步 → 撤回重算未检
  → 撤回某类全部样本后估数撤下并提示「缺少实检类别样本：控制」→
  补检后恢复 → 两线程并发改不同机器两笔均生效且明细与计数一致 →
  全部拆完返回实数（39/59/22，合计 120）。
- 试算冒烟（`scripts/smoke_simulation.py`）**全部 PASS**：120 台全检后
  6 档试算 0.51 秒完成，返回 100 轮/门槛 90/各档计数自洽，推荐量 119 台
  （达标 100 次）且确为最小达标档；试算期间把一台更正后又改回原值，
  任务变为 `invalidated` 且 `result` 为 `None`，再次轮询仍不恢复；
  重新上传换批后旧任务同样失效。
- 页面 DOM 级验证（jsdom 加载真实 `index.html`，操作运行中的服务）**全部
  PASS**：上传后显示 120 行 → 未全检时试算按钮禁用并提示 → 全检后填写
  6 档参数点「开始试算」→ 页面渲染 6 行达标统计与「推荐抽检 80 台/轮
  （最小档），达标 99 次」→ 试算期间更正一台并改回，页面提示「已失效」
  且旧建议撤下，再等一个轮询周期仍不恢复。
- 响应性与并发：500 台、6 档的试算约 0.8 秒完成，期间 `GET /api/batch`
  最大延迟 17 ms；试算进行中另一窗口更正（2 ms）/撤回（4 ms）/换批
  （`POST /api/batch`）均即时成功，旧任务随后变为 `invalidated`。
- 边界：501 台拒绝、500 台接受；非法类别/未知机器/空上传均返回 400；
  试算档位 0、等于全批、重复、超过 6 档、非整数、负误差、非整数种子
  均返回 400 且带中文原因。

## 七、未完成项 / 已知限制

1. **本环境未安装 Docker**（无 `docker`/`podman` 命令，也无
   `/var/run/docker.sock`），`docker compose up --build` 未在本机实际执行；
   Dockerfile/compose 仅做了 YAML 语法与配置核对，需在有 Docker 的环境
   再跑一次确认。本次实际运行验证用的是本地 uvicorn 单 worker。
   另：`requirements.txt` 原先锁定的 `pytest-asyncio==1.1.2` 在 PyPI 上
   不存在，会让构建时的 `pip install -r requirements.txt` 直接失败，
   已改为实测可安装的 `1.1.1`；该修正未在真实镜像构建中复验。
2. 内存存储 + 单 worker：服务重启或重新上传会清空拆检记录；没有用户/
   多批次隔离，同一时刻只保留一个批次。试算任务表也保存在内存中
   （最多保留 50 条非运行任务，超出时淘汰最旧的已完成/失效任务），
   服务重启即丢失。
3. 经验混淆矩阵直接采用样本频率，未做平滑；某类实检样本很少时概率估计
   噪声较大（门控只保证三类齐且满秩，不保证样本量充足）。因此小档位
   （如 5 台/轮）常因估数不可用或偏差大而达标次数很低，属预期行为。
4. 估数台数为折算小数（页面保留两位小数），未做取整分配；如需整数备件
   建议，可另加最大余数法取整。试算的“绝对差 ≤ 允许误差”直接比较小数
   估数与整数实数。
5. 前端轮询间隔固定 3 秒（试算任务 0.8 秒），未用 WebSocket 推送。
6. 试算为纯 CPU 计算，在 `asyncio.to_thread` 默认线程池中执行；多个用户
   同时发起大档位试算会争用线程池，但不会阻塞其他接口的读写。
